# CapstoneV2 데이터 계약

상태: **세 번째 통합에서 세 PX4 비행의 실제 수집·개수·live/offline958행 동일성과 유효 분석 창을 확인했다.** 기업 BIN도 전체 읽기·전처리·바이트 보존을 통과했지만, 시간 역행/공백 경계로 준비된50행 창은0개다. 기업 로그의 분석 준비 완료는 아니며 시각 경계/기록 지연 처리의 후속 검토가 필요하다. 실제 수치와 범위는 루트 `검증결과.md`를 따른다.

## 1. 범위와 읽는 순서

| 순서 | 파일 | 입력 → 출력 / 책임 |
|---|---|---|
| 1 | `capstone/collector.py` | UDP → 데이터그램 원문·디코딩 원문·종료 요약. 수신 전용, 저장 오류·콜백 오류를 감독자에게 전달 |
| 2 | `capstone/replay.py` | 닫힌 JSONL 또는 DataFlash BIN → 동일한 외피의 순서 있는 반복자. 원문 파일에 쓰지 않음 |
| 3 | `capstone/preprocess.py` | 외피 → 펌웨어별 물리량·인과 10 Hz 행·준비 마스크·최근 50행 창 |
| 4 | `tests/test_data.py` | 명시적인 합성 UDP/JSONL/BIN으로 계약 검사. 기업 원자료는 테스트에서 열지 않음 |
| 5 | 이 문서 | 스키마, 단위, 시계, 준비 조건, 실행 감독자와 AI 소비자의 책임 |

`main.py`, 환경 구성, 배터리 송신기, 모터 고장 제어는 각 담당 모듈의 책임이다. V1 코드나 V1 가상환경은 runtime/import 의존성이 아니다. 원본 PX4·Gazebo·pymavlink 소스를 수정하지 않는다.

AI 학습, 정규화 통계 fitting, 모델 파일, 이상/고장 분류, 열 모델, 완성 UI는 구현하지 않는다. `ready`는 **입력 가용성**이지 건강 판정·비행 허가·모델 정확도 인증이 아니다.

## 2. 수집 API와 운영 소유권

```python
Collector(host, port, output_dir, *, decoder_path=None,
          system_id=None, component_id=1, on_record=None)
collector.start()                         # 자신을 반환; 인스턴스당 한 번
collector.port                           # port=0이면 실제 할당된 포트
collector.listen_port                    # 같은 값의 읽기 속성
collector.latest("BATTERY_STATUS", max_age_s=3)  # fields dict만; 불가하면 {}
collector.latest("HEARTBEAT", since_monotonic_ns=resume_ns)  # 경계 뒤 실제 수신만
collector.snapshot()                     # counts, running, error, errors, identity
collector.stop()                         # 최종 snapshot 또는 예외; 반복 호출 가능
collector.close()                        # stop()과 동일한 종료 API
```

- `host`는 **명시한 IPv4/IPv6 숫자 주소**다. SITL은 `127.0.0.1` 또는 `::1`을 사용한다. 사용자 지정 bind 주소도 받지만 실기체 연결을 자동으로 시도하지 않는다. DNS 주소·`udp:` 연결 문자열을 받지 않는다.
- 일반 UDP socket의 `bind`/`recvfrom`만 쓴다. `connect`, `send`, `sendto`, heartbeat, TIMESYNC, stream 요청, 명령 ACK를 보내지 않는다. `SO_REUSEADDR`/`SO_REUSEPORT`를 켜지 않으며 같은 주소·포트를 나눠 받지 않는다.
- `decoder_path`에는 V2가 고정 PX4 XML에서 생성한 **신뢰하는 Python dialect**를 지정한다. 통합 경로는 `hermes/generated/px4_mavlink.py`다. 파일을 별도 모듈로 불러와 그 `MAVLink` 클래스를 쓰며 `mavutil.mavlink`나 `MAVLINK_DIALECT` 같은 전역 설정을 바꾸지 않는다. 임의 다운로드한 Python 파일을 지정하지 않는다.
- 기본 decoder는 설치된 `pymavlink.dialects.v20.common`이다. 이 기본값이 고정 PX4 development 메시지를 모두 안다고 보장하지 않는다. 실제 통합에서는 생성 dialect를 전달한다. 시작 경계에 사용 decoder 경로·SHA-256을 기록한다.
- `system_id=None`이면 지정 component에서 온 첫 **autopilot HEARTBEAT**로 system을 고정한다. MAV_AUTOPILOT_INVALID(8)인 GCS heartbeat는 선택하지 않는다. 그 전에는 `latest()`가 비어 있다. 여러 기체가 있으면 system ID를 명시한다.
- 원문은 필터 밖 메시지까지 저장한다. `latest()`만 선택 system/component를 적용한다. 같은 system의 배터리 입력 **component180**과 PX4 재출력 **component1**을 섞지 않는다. 미수신·오래된 수신·정지·실패 상태에서는 `{}`다. 값의 개별 유효성까지 인증하는 API는 아니다.
- `since_monotonic_ns=None`이 기본이며 기존 호출은 그대로다. 지정하면 같은 PC의 `time.monotonic_ns()` 비음수 정수 경계보다 **엄격히 뒤에** 수신한 표본만 반환한다. 기본 3초 신선도·기체 식별·정지/실패 검사도 함께 적용한다. 시뮬레이션/UTC ns와 혼용하지 않으며 원문의 수신 시각을 새 값으로 덮지 않는다. `Runtime.pause(False)`의 재개 확인에 사용한다.
- `output_dir/mavlink_raw.jsonl`, `output_dir/summary.json`은 새 파일이어야 한다. 기존 원문/요약을 덮어쓰거나 실패 run에 이어 쓰지 않는다. raw는 매 외피마다 flush, 정상/비정상 종료 때 fsync를 시도한다. 디스크 영구 보관·회전·전체 용량 상한은 별도 운영 책임이다.
- `on_record(envelope)`는 raw flush 뒤 수집 스레드에서 복사본으로 호출한다. `Preprocessor.consume`를 그대로 연결할 수 있다. 모든 외피 종류가 도착한다. 콜백은 신속하게 반환해야 하며 무거운 추론이나 무제한 큐를 넣지 않는다. 예외가 발생하면 수집을 실패 처리한다. 콜백 안에서 `collector.stop()`을 호출하지 않는다.
- `snapshot()`의 `datagrams`, `messages`, `saved_records`, `decode_diagnostics`, `seen_by_type`은 서로 다른 개수다. `messages`에는 `BAD_DATA`도 포함한다. 마지막 것만 `summary.json`에 저장된 성공 건수라고 오해하지 않는다. `saved_records`는 파일로 flush한 모든 외피 수다.
- 스레드·디코더의 예상 밖 예외, 저장/flush/fsync/close/콜백 실패는 `error`/`errors`에 계속 남고 `stop()`이 예외를 낸다. 요약 파일에는 가능한 범위에서 실패를 남긴다. **디스크 전체 고장으로 요약까지 못 쓰는 경우 메모리 상태·예외가 최종 근거**다. 감독자는 실행 중에도 오류를 확인해야 한다.
- `stop()`은 소유 수신 스레드를 최대 3초 기다린다. 멈춘 콜백 때문에 끝나지 않으면 TimeoutError를 내며 자원을 다른 스레드에서 강제 닫지 않는다. 이 경우 감독자는 해당 run을 실패로 처리한다. 재실행은 새 인스턴스/새 run 폴더다.

## 3. 원문 외피 `capstone.raw.v1`

모든 원문에 `schema="capstone.raw.v1"`를 쓴다. V1 원문/행 JSONL을 조용히 이 형식으로 바꾸지 않는다.

| 필드 | 의미 |
|---|---|
| `kind` | `boundary`, `datagram`, `message`, `decode_error`, `opaque` |
| `source_kind` | 실시간/저장 MAVLink는 `mavlink_udp`, BIN은 `ardupilot_bin`; 재생의 파일 경계만 `raw_jsonl` |
| `run_id`, `epoch` | 수집 run 식별자와 명시적인 원천 epoch. 수집기는 재시작마다 새 run, 현재 원천 epoch=0 |
| `record_index` | raw 저장 순서. UDP는 0부터 모든 외피에 부여; BIN은 파일 안 경계/메시지/미해석 바이트 순서. 추가 JSONL 파일 경계는 null |
| `message_name`, `message_id` | 디코딩 이름과 MAVLink ID. BIN의 이름은 `BAT`/`IMU` 등의 원래 이름이며 **MAVLink message_id는 null** |
| `source_system`, `source_component`, `packet_sequence` | MAVLink wire 헤더. sequence는 8비트 순환 번호이지 메시지별 샘플 번호/시각이 아님. BIN·손상 프레임은 null |
| `peer` | UDP 송신 주소 튜플의 JSON 배열. 발행 system/component나 인증된 상대와 같지 않음. BIN은 null |
| `receive_wall_ns` | PC `time.time_ns()` 수신 시각. UTC epoch 기반이며 NTP 변경/역행 가능 |
| `receive_monotonic_ns` | 수집 PC 단조 시계의 수신 시각. 다른 PC/run의 물리 시각과 직접 비교하지 않음 |
| `source_time` | 실제 필드의 `{field, value, unit, clock}` 또는 null. 시간 환산/보간/동기화 결과가 아님 |
| `fields` | 원래 이름의 디코더 필드. 이 단계에서 특징 단위 변환·센티널 교체·고장 정답 추가를 하지 않음 |
| `raw_hex` | `datagram`은 원래 UDP payload 전체, `message`는 해당 프레임/네이티브 BIN 레코드. 경계/설명 이벤트는 빈 문자열 |

`source_time`은 MAVLink에서 `time_boot_ms`(ms/boot), `time_usec`(µs/boot_or_unix), `time_unix_usec`(µs/unix) 순으로 존재하는 필드를 선택한다. 함께 존재하는 나머지 시간 필드도 `fields`에 남는다. `time_usec`를 크기만 보고 UTC나 sim-time으로 확정하지 않는다. BIN은 **그 레코드 자체에 실제 `TimeUS`가 있을 때만** µs/boot를 기록한다. 없는 시각을 이전 값, 파일 mtime, 수신 시각, DFReader의 보간 `_timestamp`로 만들지 않는다.

### 메시지 보존과 데이터그램 경계

- allowlist 없이 **디코더가 반환하는 모든 메시지**를 저장한다. 필터 밖 기체, component180, heartbeat, 명령 메시지, 설정, ESC 등도 원문에서 지우지 않는다. 이것은 모든 종류를 AI 특징으로 쓴다는 뜻이 아니다.
- 원 데이터그램을 먼저 `datagram` 외피로 저장하고, 그 안 메시지를 순서대로 저장한다. `datagram_index`로 연결한다. 여러 메시지는 같은 수신 시각을 공유한다. 재생 시 `datagram`을 다시 특징으로 디코딩해 중복 적용하지 않는다.
- `decode_status`는 `decoded`/`unknown`/`bad_data`다. `UNKNOWN_*`도 실제 헤더의 ID/system/component/seq와 원문을 남긴다. 알려지지 않은 CRC_EXTRA/서명까지 검증했다는 주장은 하지 않는다. `BAD_DATA`는 디코더가 잘못된 데이터로 반환한 부분이며 유효 식별자는 null이다.
- 데이터그램 사이에 프레임 조각을 이어 붙이지 않는다. 남은 부분은 `decode_error`에 바이트 수를 남기고 원 데이터그램에서 복구 가능하다. 완전한 MAVLink 프레임을 UDP 데이터그램 안에 넣는 송신 계약이다. 조각난 전송의 메시지 복원은 범위 밖이다.
- UDP 수신 성공은 송신 경로 전체의 무손실 인증이 아니다. 커널 버퍼 손실·패킷 재정렬·느린 디스크/콜백으로 인한 드롭을 sequence 차이만으로 완전히 측정하지 않는다.

### JSON 태그

`encode_json`/`decode_json`을 저장·재생·소비자 기록에 같이 사용한다.

```json
{"$float":"nan"}
{"$float":"inf"}
{"$float":"-inf"}
{"$bytes":"00ff"}
```

비유한 실수와 bytes는 위 단일 키 객체를 예약해서 보존한다. 센티널 정수는 원래 수치대로 남긴다. JSON의 비표준 `NaN`/`Infinity` 상수는 거부한다. 복구한 Python 필드에는 실제 NaN/Inf/bytes가 돌아온다. 비트 단위 NaN payload, 문자열 디코딩 전 바이트, 배열의 원시 표현은 `raw_hex`가 최종 근거다. 예약 태그와 같은 모양의 임의 사용자 dict를 payload로 추가하지 않는다.

## 4. 기록 재생과 기업 BIN

```python
iter_records(path, *, source_kind="auto", decoder_path=None)
```

- `source_kind`: `auto`, `raw_jsonl`, `ardupilot_bin`; 짧은 별칭 `jsonl`, `bin`도 허용한다.
- 파일은 `.jsonl`/`.BIN` 확장자로 구분한다. 폴더의 JSONL은 **`mavlink_raw.jsonl`, `mavlink_raw.000001.jsonl`, …**만 대상으로 삼는다. 행 JSONL·정답 JSONL·summary를 같이 읽지 않는다. base 파일 뒤 숫자 순서로 읽는다. 현재 collector 자체는 회전 파일을 만들지 않는다.
- BIN 폴더는 파일 이름의 숫자 기준 순서로 읽되 각 파일을 독립 run으로 삼는다. 혼합 폴더는 `auto`에서 거부한다. 서로 다른 비행을 시각으로 섞거나 정렬하지 않는다.
- JSONL 재생은 저장된 외피를 태그 복구 외에는 그대로 공급한다. 각 파일 앞뒤에 `scope="file"`, `file_start/file_end` 경계를 추가한다. 이것은 회전 경계이지 run 종료가 아니다. 전처리는 이 경계를 무시하고 저장된 run/epoch를 따른다.
- 닫힌 파일만 대상으로 한다. 불완전한 마지막 행, 잘못된 JSON/스키마는 **파일명:행번호가 있는 오류**로 종료한다. 망가진 행을 몰래 건너뛰지 않는다. 한 행 상한은 4 MiB다.
- `decoder_path`는 공통 호출부의 인자로 허용할 뿐 재생에서 사용하지 않는다. JSONL은 이미 디코딩되었고 BIN은 MAVLink가 아니므로 다른 MAVLink dialect로 재해석하지 않는다.

### BIN 변환의 정확한 범위

`pymavlink.DFReader.DFReader_binary`와 `recv_msg()`로 파일 순서를 따른다. `fields`는 `to_dict()`가 돌려주는 **DataFlash 필드명과 format 배율을 적용한 값**이다. 원시 정수와 이를 혼동하지 않는다. 예를 들어 `ATT.Roll`은 이미 degree이고, 추가로 centidegree를 한 번 더 나누지 않는다. `TimeUS`는 실제 원천 µs를 유지한다.

`native`에 파일 `offset`, `length`, `type_id`, `format`, `columns`, `units`를 보존한다. `FMT/FMTU/UNIT/MULT` 레코드도 모두 공급한다. `native.units`가 SI 단위를 말해도 모든 `fields`가 그 단위로 추가 변환되었다고 가정하지 않는다. 예를 들어 ArduCopter 4.4의 `BAT.CurrTot`은 실제 로거가 `consumed_mah`를 쓰고 DFReader의 `f`에는 추가 SI 변환이 없으므로 mAh다.

DFReader가 건너뛴 바이트/끝의 미완성 바이트도 `opaque` 외피에 64 KiB 이하 조각으로 남긴다. 원본 오프셋 순서대로 `message`와 `opaque`의 `raw_hex`를 이어 원본을 대조할 수 있다. `opaque`는 유효 센서 관측이 아니다. 파서 예외는 전파한다. 반복을 중간에 멈추는 호출자는 generator의 `close()` 또는 `contextlib.closing`으로 파일/mmap을 닫아야 한다. 전체 소비/예외 시에는 내부 `finally`에서 닫는다.

참고 대상은 V1의 기업 ArduCopter 4.4 BIN과 기존 전체확인보고서다. **이번 작성 작업에서는 기업 BIN에 파서를 실행하지 않았다.** 기록된 BAT0/IMU0/GPS0을 선택하는 계약이며, 센서 장착·교정·현재 MAVLink 가용성이나 비행 정상 라벨을 인증하지 않는다. V1 경로는 참고 원자료일 뿐 제품 코드의 의존성이 아니다.

## 5. 공유 전처리 API

```python
Preprocessor(firmware, *, system_id=None, component_id=1, battery_id=None,
             battery_cells=4, imu_instance=0, gps_instance=0, on_event=None)
processor.consume(envelope)   # 확정된 row/boundary 이벤트 list
processor.finish()            # 닫힌 입력의 마지막 관측 tick까지만 확정; 이후 consume 금지
processor.reset(reason="manual_reset")  # 명시적 경계; 다시 소비 가능
processor.window(group=None)  # None 또는 최근 50행 복사본
processor.snapshot()          # 행/epoch/미시각/제외 개수, 선택 ID, 마지막 시각
feature_schema(firmware)      # 특징별 unit/source/max_age_ns/required_for
preprocess_file(path, output_path, *, firmware,
                source_kind="auto", decoder_path=None, **options)
```

`firmware`는 `px4_gz` 또는 `arducopter_4_4`로 **반드시 지정**한다. 메시지 이름을 보고 모든 firmware가 같은 의미라고 추정하지 않는다. 이 값은 호출자의 생산 경로 선언이지 firmware 자동 검증 결과가 아니다. `px4_gz`는 MAVLink 외피, `arducopter_4_4`는 BIN 외피만 받는다.

- live: `Collector(..., on_record=processor.consume)`로 연결하고 `processor.on_event`에 행/경계 저장 또는 가벼운 소비 함수를 둔다. `consume`의 반환 list는 Collector가 별도로 저장하지 않는다. live 행 저장이 필요하면 콜백을 연결해야 한다.
- offline: `iter_records`의 각 외피를 **동일한 `consume`**에 공급한 뒤 `finish()`를 호출한다. `preprocess_file`이 이 흐름을 구현하고 출력 새 파일을 소유한다. 출력에는 metadata 한 행, 경계, 정렬 행만 기록한다. `on_event` 옵션을 동시에 받지 않는다.
- `preprocess_file`의 `options`는 `system_id`, `component_id`, `battery_id`, `battery_cells`, `imu_instance`, `gps_instance`다. 반환값은 `records`, `rows`, `boundaries`, `output_path`, `processor` 요약이다. 기존 출력은 거부하며 실패 중 생성된 파일은 진단용으로 남는다. 성공 반환을 확인하지 않은 일부 파일을 완성 데이터로 쓰지 않는다.
- 원문은 전부 보존하지만 전처리는 필요한 항목만 읽는다. 정의하지 않은 field/메시지를 정상 0이나 다른 특징으로 자동 대응시키지 않는다.
- PX4 battery ID를 생략하면 선택 autopilot의 첫 BATTERY_STATUS ID로 고정한다. 원문 ID는 바꾸지 않는다. 여러 배터리는 실제 출력 ID를 지정한다. component180 입력 ID0을 component1 출력 ID로 가정하지 않는다.
- **고정 stock PX4의 재출력 ID255는 통합 실행에서 실제 수신으로 확인했다.** `mavlink_receiver.cpp`의 배터리 수신 경로가 uORB ID를 기본 0으로 남기고 stream이 `id-1`을 uint8에 넣는 소스 구조와 일치한다. 원래 sender ID0이나 관측 raw의 255를 편의상 서로 바꾸지 않는다. 동일 수신 경로는 wire 온도에 /100 없이 대입하므로 stream의 ×100 왕복과 unknown 32767 처리도 신뢰할 수 없다. 온도 특징 제외·원문 보존으로 대응하며 upstream이나 송신 단위를 비표준으로 패치하지 않는다.
- `battery_cells=4`는 승인된 4S 출력의 앞 네 셀 합이다. 셀별 값 대신 첫 슬롯에 팩 전압을 보내는 경로에는 `battery_cells=1`처럼 **실제 출력 계약을 명시**한다. 알 수 없는 셀을 빼고 부분합을 정상 팩 전압으로 내지 않는다.
- ArduCopter 경로는 BAT.Instance0, IMU.I0, GPS.I0, VIBE.IMU0만 지원한다. 인스턴스 필드가 없으면 0으로 추측하지 않는다. 다른 인스턴스로 자동 fallback하지 않는다.

## 6. 특징의 의미·단위와 독립 준비 조건

모든 특징은 `values`, `mask`, `age_ns`의 같은 이름에 대응한다. 각 행은 `schema="capstone.rows.v1"`, `firmware`, `source_kind`, `run_id`, `source_epoch`, 전처리 `epoch`, `clock`, `tick_ns`를 함께 가진다. 같은 이름의 물리량이 있다고 펌웨어별 처리 경로·분포·모델 가중치가 호환되는 것은 아니다.

| 특징군 | PX4 GZ 입력 | ArduCopter 4.4 BIN 입력 | TTL / 준비 조건 |
|---|---|---|---|
| `battery_voltage_v` | BATTERY_STATUS 선택 셀 mV 합 /1000 | BAT.Volt, 팩 V | 600 ms / battery 필수 |
| `battery_current_a` | current_battery cA /100, -1 미제공 | BAT.Curr, A; 실제 음수 기록도 유지 | 600 ms / battery 필수 |
| `battery_soc_pct` | battery_remaining 0~100 | BAT.RemPct 0~100 | 600 ms / battery 필수; **SOH 아님** |
| `battery_consumed_mah` | current_consumed 비음수 mAh | BAT.CurrTot, mAh | 600 ms / 선택 항목·감소 시 경계 |
| `attitude_roll/pitch/yaw_rad` | ATTITUDE의 rad | ATT degree × π/180 | 300 ms / roll,pitch만 motion 필수 |
| `imu_accel_{x,y,z}_m_s2` | HIGHRES_IMU, body 처리·bias 보정 m/s² | IMU I0 AccX/Y/Z, AH=1 확인 | 200 ms / motion 필수 |
| `imu_gyro_{x,y,z}_rad_s` | HIGHRES_IMU, body 처리·bias 보정 rad/s | IMU I0 GyrX/Y/Z, GH=1 확인 | 200 ms / motion 필수 |
| `px4_actuator_{1..4}_command_rad_s` | ACTUATOR_OUTPUT_STATUS 앞 네 출력, GZ angular command | **없음** | 250 ms / PX4 motion 필수 |
| `ap_output_{1..4}_pwm_us` | **없음** | RCOU.C1~C4, PWM µs 명령 | 250 ms / AP motion 필수 |
| `velocity_{x,y,z}_ned_m_s` | LOCAL_POSITION_NED, 추정 속도 m/s, 아래쪽 양수 | 이번 최소 매핑에 없음 | 300 ms / 선택 |
| `px4_coning_metric_rad2` | VIBRATION.vibration_x, coning metric | **없음** | 300 ms / 선택 |
| `px4_gyro_vibration_rad_s` | VIBRATION.vibration_y, gyro metric | **없음** | 300 ms / 선택 |
| `px4_accel_vibration_m_s2` | VIBRATION.vibration_z, accel metric | **없음** | 300 ms / 선택 |
| `ap_vibe_{x,y,z}_m_s2` | **없음** | VIBE.VibeX/Y/Z, IMU0 축별 처리 진동 | 300 ms / 선택 |
| `gps_altitude_msl_m` | GPS_RAW_INT.alt mm /1000 | GPS.Alt, 이미 m | 600 ms / 선택·3D 이상 fix |
| `gps_speed_m_s` | GPS_RAW_INT.vel cm/s /100 | GPS.Spd, m/s | 600 ms / 선택·2D 이상 fix |
| `gps_hdop` | GPS_RAW_INT.eph /100 | GPS.HDop, DFReader 배율 적용 | 600 ms / 선택·2D 이상 fix |
| `gps_satellites` | satellites_visible; pinned PX4는 사용 위성 수 | GPS.NSats | 600 ms / 선택 |

- pinned PX4 stream은 `ACTUATOR_OUTPUT_STATUS.active`에 활성 bitmask가 아니라 **출력 개수**를 넣는다. 네 개 이상의 유효 슬롯이 있는지 확인한다. 이 해석은 일반 MAVLink 표준만으로 다른 firmware에 적용하면 안 된다. 출력 명령은 **실측 RPM, 모터 전류, 추력**이 아니다. 물리 모터 위치 대응도 별도 설정/검증 대상이다.
- HIGHRES_IMU의 `fields_updated` bit0~2는 accel, bit3~5는 gyro다. 켜진 bit만 갱신하며 꺼진 bit는 이전 값의 **원래 나이**를 유지한다. 잘못된 bitmap은 해당 특징을 결측으로 만든다. 실제 수신한 0은 정상적인 숫자일 수 있지만 NaN/Inf·미제공 값을 0으로 바꾸지 않는다.
- PX4 VIBRATION은 ArduPilot의 XYZ 진동과 다르다. 서로 다른 이름으로 내보내며 가상의 공통 vibration feature/정규화기를 만들지 않는다. 해당 지표가 있다는 사실만으로 특정 모터 고장을 식별할 수 있다고 주장하지 않는다.
- 기본 배터리 셀의 65535, 확장 셀의 미지원 0, 전류 -1, 음수 누적 소비, 범위 밖 SOC는 결측이다. GPS의 65535/255 및 불충분한 fix도 해당 특징을 무효화한다. AP의 실제 음수 전류를 MAVLink -1 센티널과 혼동하지 않는다.
- 배터리 온도는 특징에서 제외한다. AP 온도 0이나 stock PX4의 온도 왕복값을 열 측정으로 인증하지 않는다. AP 저항·보정 전압·설정 용량을 SOH 정답으로 만들지 않는다.

### 그룹별 준비

`battery_ready`는 그 행의 팩 전압·팩 전류·SOC만 요구한다. `motion_ready`는 그 행의 펌웨어별 네 출력 명령·roll/pitch·IMU 여섯 축만 요구한다. **전체 특징을 한꺼번에 필수로 묶지 않는다.** GPS·진동·누적소비·속도가 없다고 준비된 배터리 분석까지 막지 않는다. 준비 기준은 AI 팀이 확정한 이상 판정 성능 요구와 동일하다는 주장이 아니다.

`window_battery_ready`/`window_motion_ready`는 최근 50행 모두가 해당 그룹 준비 조건을 만족할 때만 true다. 창이 아직 50행이 아니면 false다. `window("battery")`와 `window("motion")`은 그 조건이 아니면 None이며 `window()`는 결측을 포함하더라도 완성된 50행 복사본을 준다. 겹치는 창 배열을 매 행마다 디스크에 복제하지 않는다. 내부 deque는 최근 50행만 보존한다.

## 7. 인과 정렬·시계·공백

1. **UDP 정렬 시계는 receive_monotonic_ns**, **BIN 정렬 시계는 실제 TimeUS×1000**이다. 행의 `clock` 값은 각각 `receive_monotonic_ns`/`source_boot_ns`다. BIN을 과거 PC 수신 스트림이라고 부르거나 두 시계를 UTC로 임의 통합하지 않는다.
2. epoch의 첫 유효 입력 시각을 기준으로 100 ms tick을 만든다. 입력 시각보다 앞선 tick을 먼저 확정하고 현재 입력을 반영한다. tick과 같은 시각의 모든 입력은 더 큰 시각이 올 때까지 보류한다. 미래 값 backfill·선형 보간은 없다.
3. 허용 나이 안에서만 인과적 마지막 값 유지가 가능하다. TTL 초과 또는 명시적 잘못된 업데이트는 `values[name]=null`, `mask[name]=false`다. 미관측 `age_ns`는 null, 관측 후 만료/무효인 경우에는 경과 나이를 남긴다. 유효한 실제 0과 다르다.
4. 같은 종류의 같은 원천 timestamp가 다시 와도 feature age를 갱신하지 않는다. 메시지 종류 간 원천 시계를 서로 비교하지 않는다. BATTERY_STATUS에는 생성 시각이 없으므로 동일 값 재송신과 실제 새 동일 측정을 구별할 수 없다는 한계가 남는다.
5. run/명시 epoch 변경, 알려진 `reset`, 정렬 시계 역행, 인접 선택 관측 사이 **1초 초과 공백**, 동일 종류 원천 시각 역행, 배터리 누적 소비 감소는 창을 끊는다. 경계 직전 마지막 관측 tick까지만 확정하고 긴 공백을 수천 개 가짜 행으로 채우지 않는다. 새로운 epoch의 deque·freshness는 비운다.
6. 전체 스트림은 계속되는데 일부 센서만 끊기면 그 센서의 mask가 TTL 뒤 false가 된다. 그 그룹의 유효 창은 다시 연속 50행을 받아야 준비된다. unrelated 센서의 결측을 이유로 다른 그룹을 전역 차단하지 않는다.
7. 역행이 정말 reboot인지, 전송 재정렬인지, 로그 쓰기 순서 차이인지는 자동 인증하지 않는다. 안전하게 분리하므로 순서가 흔들리는 실제 BIN에서 epoch가 자주 끊길 수 있다. 원래 순서를 보존하며 미래 레코드를 당겨 정렬하지 않는다.
8. nominal 5초 창은 10 Hz의 50행이다. 첫–끝 표본 간격은 4.9초다. 창의 원천 시간 보장과 live 수신 시간 보장은 다르다. pause·가속 시뮬레이션에서 서로 같은 초라고 가정하지 않는다.
9. live 침묵에는 PC 타이머로 행이나 창을 추가하지 않는다. `finish()`는 닫힌 기록/정상 종료 때만 쓴다. `window()`는 새 입력이 없으면 이전 창을 반환할 수 있으므로 소비자가 `(run_id, epoch, tick_ns)` 중복과 마지막 수신의 별도 wall timeout을 확인해야 한다. 과거 준비 창을 새 판정처럼 반복하지 않는다.

## 8. 관측·정답·품질 경계

원문 저장은 무손실에 가까운 수신 증거를 남기는 책임이며 모든 필드가 AI 입력은 아니다. 전처리는 위 특징 이름만 명시적으로 선택한다. profile ID, 용량/저항 catalog, 고장 대상 모터, 적용 배율·발생 계획·적용 시각 등 정답을 특징에 합치지 않는다. run ID/파일 경로/firmware/epoch는 관리·경계 메타데이터이며 모델 입력으로 숫자 인코딩하지 않는다. 비행/run 단위 분할 전에 겹친 창을 임의로 섞지 않는다.

입력 source/firmware 선언이 틀렸거나 저장이 일부 실패한 run을 자동으로 정상 TRAIN이라고 부르지 않는다. 수신·프로세스 건강도, 각 특징 가용성, 모델 준비도, 정상/고장 판정은 별도 개념이다.

## 9. 확인한 소스와 남은 검증

소스 열람 근거:

- V2 고정 PX4의 `src/modules/mavlink/streams/{ACTUATOR_OUTPUT_STATUS,BATTERY_STATUS,HIGHRES_IMU,VIBRATION}.hpp`와 `src/modules/simulation/gz_bridge/GZMixingInterfaceESC.cpp`.
- 같은 checkout의 `src/modules/mavlink/mavlink/message_definitions/v1.0/common.xml`의 BATTERY_STATUS 등 원문 단위/센티널.
- V2 `.venv`의 `pymavlink/DFReader.py`: `DFMessage.to_dict`, `__getattr__`, `DFReader_binary`, `_parse_next`, `close`. 같은 환경의 v20 common decoder에서 `parse_buffer`, `buf_len`, UNKNOWN/BAD_DATA 반환 구조.
- ArduPilot 공식 `Copter-4.4.0` 소스의 `libraries/AP_{InertialSensor,GPS,AHRS,BattMonitor,Logger}/LogStructure.h`, `libraries/AP_BattMonitor/AP_BattMonitor_Logging.cpp`. AP 각속도 rad/s, 진동 m/s², 자세의 degree 배율, PWM µs, 실제 consumed_mah 저장을 확인했다.
- V1의 `simulation/docs/ai-telemetry-contract.md`, `hermes/bin-log-inspection/비행로그_전체확인보고서.md`는 읽기 전용 참고다. V1 통과 결과를 V2 검증으로 이전하지 않았다.

통합 검증에 작성해 둔 검사: receive-only/독점 포트, component/system 필터, 태그·원문 roundtrip, 콜백/IO 실패 유지, 회전 파일 순서/불완전 JSONL 오류, 실제 DFReader로 합성 BIN 시각·원시 바이트 대조, 미래 누출 금지, stale/센티널/IMU bitmap, 독립 준비 창, run/공백/시계 역행, live/offline 같은 행과 중복 창 저장 부재.

세 번째 통합 실행에서 생성 PX4 dialect의 실제 수신, 배터리 wire 대응과 출력 ID255, live/offline 행 일치와 유효 창, 지정 BIN 전체 파싱·바이트 재구성·epoch 경계 양상을 확인했다. 수치와 한계는 루트 `검증결과.md`를 따른다. 수집 디스크/장시간 부하 내구성, 모든 메시지·필드의 보편적 지원, 실제 고장 판정 성능은 미검증이다. 기업 BIN은 항목·단위·기록 주기 참고용이며 학습/검증/시험 데이터가 아니다. 기록된 필드·주기가 실시간 MAVLink에서도 동일하게 제공된다고 가정하지 않는다.

DFReader 자체는 파일 mmap과 인덱스를 만들므로 **전체 replay 메모리가 O(50)이라는 주장은 하지 않는다**. O(50) 제한은 전처리의 소비자 창에 관한 것이다. 열린 JSONL tail-follow, 데이터그램 간 프레임 조합, 자동 로그 회전, normalized dataset/학습 모델은 이번 구현에 없다.
