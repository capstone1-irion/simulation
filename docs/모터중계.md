# 모터 명령 중계와 네이티브 인터페이스

상태: **세 번째 통합 실행에서 native 합성30개, 실제 비행 중 패스스루·모터1 약화·자동 만료/clear·joint/자세 반응을 확인했다.** 0.9구간 joint/원명령 비율 중앙값은0.9000220073360418이었다. 모터2~4 개별 고장 비행·직접 경로 대비 지연 동등성·모든 실패분기는 별도 미검증이다. 결과는 루트 `검증결과.md`를 따른다. 아래 명령 예시 자체를 별도 수행한 것으로 해석하지 않는다.

## 1. 파일과 읽는 순서

| 순서 | 파일 | 역할 / 주요 호출자 |
|---|---|---|
| 1 | `models/capstone_x500/model.sdf` | 실험 입력 경로와 stock 모터 설정. Gazebo가 읽는다. |
| 2 | `native/motor_fault.cpp` | 원래 PX4 명령 수신, 상시 중계, 수동 고장 슬롯 하나, 상태/정답 관측. Gazebo system plugin이다. |
| 3 | `native/gz_feed.cpp` | StringMsg.data를 stdout으로 옮긴다. Python 실행기가 Gazebo보다 먼저 시작한다. |
| 4 | `config/server.config` | 독립 Gazebo 서버의 물리·생성·장면·비행 센서 시스템을 명시한다. |
| 5 | `CMakeLists.txt` | 위 네이티브 코드만 설치 Gazebo 라이브러리로 빌드한다. |
| 6 | `models/capstone_x500/model.config` | resource 검색용 모델 메타데이터. |

`motor_fault.cpp`는 `Mailbox` → `Status`/`Request` → `Configure` → `PreUpdate` → `PostUpdate` → `Reset`/소멸자 순으로 읽는다. transport callback은 mutex로 보호한 공유 mailbox만 값으로 캡처한다. callback이 plugin의 `this`, ECM 또는 반환된 함수의 지역 변수를 붙잡지 않는다.

## 2. 승인된 경로와 변경하지 않은 것

정상과 고장에서 **프로세스와 topic 연결은 동일**하다.

| 단계 | 생산자 → 소비자 | 값의 의미 |
|---|---|---|
| 원명령 | PX4 → MotorFault | 요구 각속도 `Actuators.velocity`, rad/s |
| 중계 출력 | MotorFault → stock `MulticopterMotorModel` 네 개 | 정상 원문 통과, 고장 시 선택 요소에만 배율 적용 |
| 물리 | stock motor → Gazebo 물리·센서 | 기존 필터, 힘, 모멘트 계산 |
| 상태 | MotorFault → gz_feed → Python | 원명령·SIM 시각과 별도로 출력/고장/joint 정답을 기록 |

초기/정상 상태는 모든 모터 배율 1이다. 고장 시점에 plugin을 켜거나 끄지 않고 우회 경로로 전환하지 않는다. 기간 만료 또는 `clear` 후 원문 통과로 돌아간다. 중계 실패는 실험 실패이며, raw topic으로 되돌리거나 0 명령을 만들어 정상처럼 계속하지 않는다.

기체는 `model://x500_base`를 `merge="true"`로 포함한다. 원본 질량·관성·센서·관절·모터 상수·회전 방향을 유지하고 네 stock 모터의 `commandSubTopic`만 `command/motor_speed_applied`로 바꿨다. V2의 `capstone::MotorFault` plugin을 앞에 추가했다. 원본 PX4/Gazebo C++, 외부 checkout, V1, 사용자 HOME 설정에는 쓰지 않는다. 별도 힘/열/GUI 모델은 없다.

소스 열람 기준:

- PX4 `v1.17.0`, `d6f12ad1c4f70ad3230afd7d86e971421e02fef4`.
- 그 checkout의 `Tools/simulation/gz`, `b6127f4ec20de867e215fb5f78ae88b80f371909`. `models/x500/model.sdf`, `models/x500_base/model.sdf`, `worlds/default.sdf`를 읽었다. V1 모델은 최초 참고에만 사용했고 제품 참조 경로는 V2의 새 의존성이다.
- PX4 `src/modules/simulation/gz_bridge/GZMixingInterfaceESC.cpp`: `init`은 실제 모델 이름으로 raw topic을 만들고 `updateOutputs`는 mixer 출력을 `velocity`에 싣는다.
- 설치 헤더: gz-sim8 8.15.0, gz-transport13 13.6 계열, gz-msgs10 10.4 계열 및 gz-plugin2. CMake imported target 이름도 설치 파일로 확인했다.

## 3. 정확한 topic과 실행 이름

SDF 파일의 기본 이름 대신 `gz::sim::Model::Name(ecm)`의 **런타임 이름**을 사용한다. `capstone_x500_31`처럼 실행별 이름을 지정해도 하드코딩한 `x500`으로 연결하지 않는다. 이름은 비어 있지 않은 ASCII 영숫자·`_`·`-`·`.` 조합이어야 한다. 잘못된 이름을 임의 정규화하지 않는다.

| 용도 | 경로 | Gazebo 메시지 |
|---|---|---|
| 입력 | `/<model>/command/motor_speed` | `gz.msgs.Actuators` |
| 출력 | `/<model>/command/motor_speed_applied` | `gz.msgs.Actuators` |
| 제어 서비스 | `/capstone/<model>/fault` | 요청·응답 모두 `gz.msgs.StringMsg` |
| 상태 topic | `/capstone/<model>/status` | JSON 문자열을 담은 `gz.msgs.StringMsg` |

모터 C++는 `robotNamespace`가 없을 때 실제 모델 이름을 사용하고 그 뒤에 `commandSubTopic`을 붙인다. PX4 ESC 경로에는 `/model/` 접두사가 없다. SDF에도 `robotNamespace`를 고정하지 않았다.

입력에는 유한한 비음수 velocity가 최소 네 개 있어야 한다. 추가 velocity, header, position, normalized 및 protobuf unknown fields는 복사해 보존한다. position/normalized의 비유한 값도 거부한다. 정상 출력에서는 재배열·clamp·타임스탬프 수정이 없다. 1000 rad/s를 넘는 유한 입력도 중계는 그대로 보내며 stock 모터의 기존 상한 처리가 따로 존재한다. 이 경계 검사는 실제 x500 운영 범위를 넓힌다는 뜻이 아니다.

중계는 매 진행 tick에서 **가장 최근 수신한 메시지**로 출력 하나를 생성한다. 한 tick 사이에 여러 원명령이 오면 마지막 메시지를 사용하며 모든 원명령을 재생하는 큐가 아니다. `input_seq`가 건너뛰는 경우를 숨기지 않는다.

## 4. 모터 번호·위치·단위

서비스의 모터 번호는 **1-based**, protobuf/SDF는 **0-based**이다. 아래 위치는 `x500_base`의 rotor link pose이며 단위는 m, 모델 body FLU(+x 전방, +y 좌측, +z 위)이다. PX4의 FRD(+y 우측, +z 아래) 좌표와 혼동하지 않는다. PX4 allocator의 별도 arm 파라미터로 SDF 위치를 덮어쓰지 않았다.

| 서비스 motor | velocity 인덱스 / motorNumber | 관절 | 모델 좌표 (x, y, z) | 위치 | stock 방향 |
|---|---|---|---|---|---|
| 1 | 0 | `rotor_0_joint` | (0.174, -0.174, 0.06) | 앞-오른쪽 | ccw |
| 2 | 1 | `rotor_1_joint` | (-0.174, 0.174, 0.06) | 뒤-왼쪽 | ccw |
| 3 | 2 | `rotor_2_joint` | (0.174, 0.174, 0.06) | 앞-왼쪽 | cw |
| 4 | 3 | `rotor_3_joint` | (-0.174, -0.174, 0.06) | 뒤-오른쪽 | cw |

- `command_rad_s`: PX4가 요구한 각속도 크기. 실제 회전 측정값 또는 RPM이 아니다.
- `output_rad_s`: 중계가 생성하여 publish 성공을 받은 요구 각속도 크기. 추력 적용 확인이 아니다.
- `joint_rad_s`: PostUpdate의 `JointVelocity[0] × 10`. stock `rotorVelocitySlowdownSim=10`을 복원한 **부호 있는** 회전자 각속도 정답이다. ccw는 양수, cw는 음수이며 절댓값으로 바꾸지 않는다. 관측 component가 없거나 값이 비유한이면 해당 요소는 `null`; 명령으로 대체하지 않는다.
- 이 plugin은 `JointVelocity` 관측을 요청할 뿐 joint 명령·force·`Actuators` component를 생성하거나 덮어쓰지 않는다.
- 배율 0.7은 명령 각속도 배율이다. 실제 추력 70%, 전기 효율 70%, 특정 ESC 고장 원인을 의미하지 않는다. stock 응답 필터와 운동 반응을 별도로 관찰해야 한다.

## 5. 수동 고장 서비스

`StringMsg.data` 문법:

```text
set <motor: 1..4> <scale: 0 < 값 <= 1> <duration_seconds: 0 < 값 <= 120>
clear
status
```

숫자는 유한해야 하며 여분 인자는 거부한다. 모터 토큰은 정확히 `1`, `2`, `3`, `4` 중 하나다. `set 1 0.7 10`은 모터 1에 10 SIM 초 동안 0.7 배율을 요청한다. 배율 0은 허용하지 않는다. 배율 1도 명시적 이벤트로 수락하지만 수치상 정상 통과다.

- 수락은 mailbox의 **한 개 대기 슬롯**에 넣는 것뿐이다. 이미 pending이면 `pending_command`로 거부하며 이전 명령을 덮어쓰지 않는다. active 중 새 `set`은 `fault_already_active`로 거부한다. 필요하면 `clear` 적용 확인 후 새 `set`을 보낸다.
- `set`/`clear`를 수락할 때만 `accepted_revision`이 증가한다. `status`와 거부 요청은 revision을 바꾸지 않는다.
- `set`은 입력이 정상이고 시계가 실제로 진행하는 다음 PreUpdate에서 시작한다. 같은 tick의 출력 publish가 성공한 뒤에만 `applied_revision`을 올린다. `clear`도 다음 진행 tick에서 원문 출력을 publish한 뒤 적용으로 기록한다.
- pause 중 요청 수락/`status` 조회는 가능하지만 적용 revision과 기간은 진행하지 않는다. 신선한 진행 시계가 없는 callback에서 캐시된 명령에 고장을 적용하지 않는다.
- duration은 `fault_started_s`부터의 SIM 초이다. 만료 시각 이상인 첫 진행 tick에서 패스스루로 복귀한다. 만료는 새 수동 요청이 아니므로 revision은 증가하지 않고 `fault_active`, `last_transition_s`가 바뀐다. 물리 tick보다 짧은 duration도 최소 한 번의 출력 구간으로 양자화될 수 있다.
- 오류를 지우는 명령은 없다. latched failure에 `clear`를 보내도 복구하지 않는다. 새 실행이 필요하다.

응답은 상태 객체에 `ok`와 `request_error`를 더한 JSON이다. Gazebo 서비스 callback의 반환 true는 응답 전송 처리를 뜻하고, 요청 수락 여부는 **JSON `ok`**로 확인해야 한다. `status`의 `ok=true`도 실험 건강 상태를 보증하지 않는다. 별도로 `error`/`fatal`을 읽는다.

최초 Gazebo tick 전에는 실제 SIM 시각이 없으므로 서비스가 `{"ok":false,"request_error":"clock_not_ready"}`만 응답한다. 허위 0초나 wall 시각을 넣지 않는다. 첫 실제 tick부터 완전한 상태 schema가 나온다.

최종 검증 단계용 호출 예시:

```sh
gz service -s /capstone/capstone_x500_31/fault \
  --reqtype gz.msgs.StringMsg --reptype gz.msgs.StringMsg \
  --timeout 2000 --req 'data: "status"'

gz service -s /capstone/capstone_x500_31/fault \
  --reqtype gz.msgs.StringMsg --reptype gz.msgs.StringMsg \
  --timeout 2000 --req 'data: "set 1 0.7 10"'
```

Python은 수락 응답의 revision을 기억하고 실제 상태의 `applied_revision`이 그 값이 되는 것을 제한 시간 안에 기다려야 한다. 서비스 CLI의 성공/응답 도착이나 `accepted_revision`만으로 고장을 적용했다고 기록하면 안 된다. 대기 중 `fatal`, 입력 단절, 프로세스 종료가 나오면 실패다. 자동 재전송은 중복 요청이 될 수 있으므로 timeout 후 먼저 `status`로 기존 revision/pending을 확인한다.

**`applied_revision`의 정확한 의미는 중계 출력 생성/publish 성공이다. stock 모터의 소비 ACK, joint 응답, 실제 힘 적용 또는 기체 운동의 증거가 아니다.** 출력 topic·joint·기체 반응 검증은 별도다.

## 6. 상태 JSON 계약 (`capstone.motor.v1`)

첫 입력 전에도 실제 SIM tick부터 상태를 발행한다. 이때 `command_rad_s=null`, `error="no_input"`, `fatal=false`, `ready=false`, `input_seq=0`이다. Python은 시작 구간에만 이를 기다릴 수 있다. 한번 정상 입력을 얻은 뒤의 invalid/stale/reset은 영구 실패로 남는다.

| 필드 | 의미 |
|---|---|
| `schema`, `model` | 고정 schema 문자열, 실제 모델 이름 |
| `sim_time_s` | 마지막 UpdateInfo.simTime의 초 단위 JSON float. UNIX/wall 시각이 아님 |
| `input_seq` | 유효한 raw 메시지마다 증가한 수신 카운터를 PreUpdate에서 snapshot한 값. 같으면 새 raw 입력이 아님 |
| `input_age_s` | 마지막 유효 수신에 연결한 SIM 시각과 현재 SIM 시각 차이. 입력 전 `null` |
| `command_rad_s` | 원명령 앞 네 요소; 입력 전 `null` |
| `output_rad_s` | 마지막 성공 출력 앞 네 요소; 첫 성공 전 `null`. 오류 시 마지막 과거 값을 보존하며 정상으로 해석하면 안 됨 |
| `fault_active`, `motor`, `scale` | 마지막 성공 출력의 고장 상태. 정상은 false, 0, 1 |
| `accepted_revision`, `applied_revision` | 요청 수락과 출력 생성 확인을 분리한 정수 카운터 |
| `error` | 건강할 때 `null`; 입력 전 `"no_input"`; 실패 시 고정 오류 코드 문자열 |
| `joint_rad_s` | 네 관절 관측 정답, signed rad/s. 결측 요소는 `null` |
| `output_input_seq`, `output_sim_time_s` | 마지막 출력의 입력 카운터와 SIM 시각. 출력 전 0 / `null` |
| `fault_started_s`, `fault_until_s` | 현재 고장의 실제 시작 / 예정 만료 SIM 시각. 고장이 없으면 `null` |
| `last_transition_s` | 마지막 성공 set/clear/자동 만료 출력의 SIM 시각. 아직 없으면 `null` |
| `paused`, `pending`, `ready`, `fatal` | 관측된 pause, 대기 슬롯, 정상 입력+성공 출력 이력, 영구 실패 여부 |
| `input_wall_age_s`, `clock_wall_age_s` | 입력 snapshot 수신 / 마지막 진행 tick 이후의 monotonic wall 경과 초. 초기 `null` 가능; SIM 적분에 사용 금지 |

`input_age_s`는 **수신측 신선도**다. 이 PX4 producer는 Actuators에 송신 시각을 넣지 않으므로 생산자 시각/네트워크 지연으로 가장하지 않는다. callback은 마지막으로 관측한 SIM tick을 수신 시각에 연결한다. 첫 clock 이전 입력은 첫 실제 관측 tick에 연결한다. 원본 header는 어느 경우에도 변경하지 않는다.

상태는 PreUpdate의 입력/출력 snapshot과 PostUpdate의 관절 관측을 묶는다. pause 또는 실패 중에는 `command_rad_s`가 최신인데 출력은 과거일 수 있으므로 `output_input_seq`, `output_sim_time_s`, `error`를 확인한다. 서비스 응답은 마지막 snapshot을 읽으며 새 물리 계산이 아니다.

진행 중 목표 주기는 0.05 SIM 초(약 20 Hz)이며 최초 입력 전에도 같다. tick 양자화와 전이 발행으로 간격은 달라질 수 있다. 상태 전이는 주기와 별도로 발행한다. pause 때에도 PostUpdate가 호출되면 약 1 wall 초 heartbeat를 발행하지만 **같은 `sim_time_s`**이며 적분/새 입력의 증거가 아니다. 감독자는 명시적 pause 상태로 진행 watchdog을 억제하고 서비스 조회를 사용할 수 있다. 같은 SIM 시각을 받아 배터리 적분을 다시 하거나 timestamp를 보정해서는 안 된다.

## 7. 단절·실패·우회 방지와 지연 한계

- 시작의 `no_input`은 실패 latch가 아니다. 최초 입력/상태/연결은 Python이 wall 제한(연결 시도당 최대 120초 이내)을 둔다.
- 정상 입력 이후, 진행 tick에서 `input_age_s > 0.5`이면 `input_stale_sim`으로 영구 실패한다.
- 입력이 오지 않는 진행 구간의 wall 경과가 2초를 넘으면 `input_stale_wall`로 영구 실패한다. pause에 머문 wall 시간은 이 보조 제한에 적분하지 않는다. `input_wall_age_s` 자체는 실제 전체 수신 경과를 보여준다.
- `invalid_input`, advertise/subscribe/service/publish 실패, reset·rewind·시계/iteration 불연속도 첫 오류가 보존된다. 나중의 정상 입력이나 `clear`로 지우지 않는다. reset 후 별도 epoch를 자동으로 시작하지 않는다.
- 모델의 `components::Actuators`는 stock motor에서 transport보다 우선한다. Configure와 매 Pre/PostUpdate에서 이를 찾으면 `competing_actuators_component`로 실패한다. component를 삭제/조작해서 문제를 숨기지 않는다. 다른 시스템이 같은 tick 중간에 component를 만들면 PostUpdate에서 뒤늦게 검출될 수 있으므로 해당 run의 물리 결과를 무효 처리한다.
- 다른 발행자가 applied topic에 주입하는 경로까지 인증하는 보안 시스템은 아니다. 실행별 partition에는 이 실험의 승인된 프로세스만 연결한다. 감독자는 stock motor 구독과 정답 관측까지 별도 검증한다.
- 실패하면 새 출력은 중단하지만 stock motor는 이전 명령을 보유할 수 있다. 따라서 **오류만 표시하고 시뮬레이션을 계속하는 운영은 금지**다. Python은 error/침묵/프로세스 종료를 실험 실패로 기록하고 소유한 실행을 중지해야 한다. plugin이 0 명령이나 정상 패스스루를 대신 보내지는 않는다.
- 시뮬레이터가 완전히 멈추면 plugin의 tick 기반 감지도 멈춘다. Python의 상태 수신·SIM 진행 wall watchdog이 필수다. pause를 요청하지 않았는데 clock이 멈추면 이를 정상 pause로 추정하지 않는다.
- 이 구현은 최신 입력 mailbox, 다음 진행 tick, Gazebo transport, stock motor 순서를 거친다. 같은 tick에 stock motor가 소비한다는 보장이나 실시간 무지연 주장은 없다. 일반 수치가 정상 통과하는지와 기존 직접 연결 대비 지연/비행 동등성은 별도 검증 항목이다. 상태의 20 Hz는 모터 원명령의 전체 기록 주기가 아니다.

## 8. gz_feed와 Python 경계

```sh
hermes/build/native/gz_feed --topic /capstone/capstone_x500_31/status
```

- 비어 있지 않은 유효한 `GZ_PARTITION`과 절대 topic을 요구한다. 값의 실행별 고유성은 부모 실행기가 보장한다. 빈/default 공유 연결로 조용히 대체하지 않는다.
- 한 번 즉시 Subscribe하고 실패하면 종료한다. Gazebo 발견 전에도 시작할 수 있으며 별도 재시도 루프나 임의 지연은 없다. stderr의 `subscribed`는 로컬 등록 확인이지 메시지 도착/모델 검증이 아니다.
- stdout은 수신한 `StringMsg.data`에 개행 하나를 붙인 원문만 제공한다. JSON 해석·단위 변환·시간 생성·제어 기능은 없다. OS write로 버퍼링 없이 내보낸다. stderr를 stdout에 합치지 않는다.
- transport callback의 독립 공유 상태를 사용하며 대기는 256행, 메시지는 1 MiB까지다. 한도를 넘으면 조용히 행을 버리지 않고 실패 종료한다. 막힌 stdout은 nonblocking write/poll로 다루며 SIGINT/SIGTERM으로 종료 가능하도록 했다. 세 번째 통합의 세 run에서 정상 종료를 확인했지만 막힌 pipe 동작은 별도 미검증이다.
- exit 2는 인자/환경 오류, exit 1은 subscribe/버퍼/출력/예외/구독 해제 오류, exit 0은 요청된 정상 종료다. 갑작스러운 stdout EOF나 process exit는 Python에서 실패로 다룬다. 의도적 종료 때의 마지막 미완성 줄은 정상 완결 기록으로 저장하지 않는다.
- Python은 feed를 Gazebo보다 먼저 시작하고 stdout을 계속 소비한다. 최초 상태·침묵 제한, SIM 진행 감시, pause 허용, 종료/정리는 Python의 책임이다.
- 배터리 입력은 `command_rad_s`와 진행하는 `sim_time_s`다. 적용 후 출력·고장 대상·배율·joint는 **ground truth 전용**으로 분리하여 저장한다. AI 실시간 특징에 섞지 않는다. 입력 결측/실패를 배터리 부하 0으로 치환하지 않는다.

## 9. 빌드·실행 환경 연결 (운영 예시)

C++17, 설치된 Gazebo Harmonic 공식 라이브러리와 표준 라이브러리만 사용한다. JSON 작성을 위해 새 런타임 라이브러리를 설치하지 않는다. PX4 타깃을 추가하거나 `.venv`를 조작하지 않는다.

최종 통합 검증 때 프로젝트 루트에서:

```sh
cmake -S . -B hermes/build/native -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build hermes/build/native
```

타깃과 기본 단일 구성 빌드 산출물:

- `MotorFault` → `hermes/build/native/libMotorFault.so`, plugin 이름 `capstone::MotorFault`.
- `gz_feed` → `hermes/build/native/gz_feed`.

부모 실행기가 Gazebo, PX4, feed, 서비스 클라이언트에 **같은 실행별 partition**을 전달한다. 아래는 프로젝트 루트를 현재 디렉터리로 둔 환경 형식 예시이다. `RUN_ID`는 실행기가 지정한 고유값이어야 한다.

```sh
export GZ_PARTITION="capstone_${RUN_ID}"
export GZ_SIM_SYSTEM_PLUGIN_PATH="$PWD/hermes/build/native"
export GZ_SIM_RESOURCE_PATH="$PWD/models:$PWD/external/PX4-Autopilot/Tools/simulation/gz/models:$PWD/external/PX4-Autopilot/Tools/simulation/gz/worlds"
export GZ_SIM_SERVER_CONFIG_PATH="$PWD/config/server.config"
```

원본 의존성 경로가 없다면 먼저 환경 구성을 완료한다. V1 resource/build 경로를 끼워 넣어 성공처럼 만들지 않는다. 모델은 `model://capstone_x500`로 선택하고 실제 spawn/include 이름과 PX4의 기존 모델 연결 이름을 일치시킨다. stock `x500`을 spawn하면 중계 plugin이 없으므로 유효한 실험이 아니다.

서버 설정에는 Physics, UserCommands, SceneBroadcaster, Contact, Imu, Magnetometer, AirPressure, NavSat가 있다. 서버를 시작한 **뒤** PX4 자식 환경에만 설정해도 이미 뜬 서버에는 적용되지 않는다. 선택 world에 별도 system plugin이 있으면 server-config 로딩 정책/중복을 확인해야 한다. 읽은 pinned `default.sdf`에는 world system plugin 선언이 없다. HOME 전역 설정은 바꾸지 않는다.

## 10. 검증 체크리스트와 현재 경계

아래는 구현 당시 작성한 전체 체크리스트다. 세 번째 통합 실행에서 빌드·로딩·패스스루·모터1 약화·joint/기체 반응·pause/resume·자동 만료/clear·정상 종료와 데이터 분리를 확인했다. 이 목록 전체가 통과했다는 뜻은 아니다. 모터2~4 개별 비행, 직접 경로 대비 지연/동등성, 모든 단절/reset/출력 실패, 막힌 stdout·지연 callback 스트레스는 미검증이다. 실제 범위는 루트 `검증결과.md`를 따른다.

1. CMake 빌드·plugin 로딩·실제 runtime 이름과 discovery, 입력 전 `no_input` 상태 수신.
2. 정상 원문 필드 보존, 네 모터 패스스루, 추가 경로/competing component 부재, stock 대비 지연과 비행 동등성.
3. 모터 1..4의 요청/적용 revision, 다른 세 채널 보존, 자동 만료·clear, 한 슬롯 거부, invalid 요청.
4. 출력 generation과 별도로 **실제 joint/기체 운동 반응**, signed 관측·slowdown 복원·모터 위치.
5. pause에서 적분/고장 기간/적용 revision 정지 및 `status` 응답, resume, reset/시계 불연속 영구 실패.
6. invalid/NaN/짧은 배열/stale 입력, status 또는 feed 침묵, 잘못된 partition, output 실패의 감독자 중단 경로.
7. 정상 종료·늦은 callback·막힌 stdout·소유 프로세스 정리, raw 명령/정답 데이터 분리와 저장.

실패 시 결과를 보존하고 추가 실행 승인을 받는다. 중계 출력이 publish됐다는 이유만으로 물리 적용 또는 전체 검증 통과를 선언하지 않는다.
