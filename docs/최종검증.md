# 최종 통합 검증

이 문서는 **실행 전 합격 기준과 경계**다. 실제 결과는 루트 `검증결과.md`와 `hermes/verification/<attempt>/report.json`을 따른다. 테스트 파일이 있다는 것과 통과했다는 것은 다르다.

2026-10-10 현재 기본 통합 검증은 승인된 세 번째 실행에서 통과했다. 아래 명령은 최초/추가 실행의 구성 기록이며 문서 최신화나 Git 배포 때 다시 실행하라는 지시가 아니다. 후속 GUI 실패와 headless 정상 종료는 결과 문서에 별도 보존한다. 기업 BIN은 현재 관측 항목·단위·기록 주기 참고용이다. 선택 BIN 검사 이력을 학습/검증/시험 데이터 지정이나 유효 분석 창 확보 의무로 해석하지 않는다.

사용자 지시에 따라 구현 중 제품 import·시험·빌드·시뮬레이션을 실행하지 않고, 모든 코드와 문서가 준비된 후 아래 실행기 한 번으로 검증한다. 실패하면 해당 단계와 이전 결과를 보존하고 중단한다. 원인을 고치고 다시 실행하려면 추가 승인을 받는다. 결과 폴더 재사용/덮어쓰기·내부 자동 retry는 없다.

## 1. 단 한 번 실행할 단계

| 단계 | 실제 확인 방법 | 실패 기준 |
|---|---|---|
| 원본·revision | 고정 PX4 HEAD와 submodule 포함 Git 상태 확인 | revision 불일치·원본 변경 |
| Python 합성 검사 | `test_battery`, `test_data`, `test_runtime` unittest를 한 번 실행. 콘솔 응답 경계와 resume의 새 수신/시계/제한/오류/종료 경계 포함 | 실패·오류·skip |
| 빌드 | 새 out-of-source PX4/V2 native 빌드, 고정 XML dialect 생성 | 명령 오류·시간 초과 |
| native 합성 검사 | 같은 구현의 입력 검사·1~4 문법·pending·실패 latch | 실제 비행과 구분한 경계 검사 실패 |
| 정상 기준 run | 기준 배터리/SOC 0.95, 지상 3.2초 wall pause와 새 heartbeat/시계 복귀, 정상 이륙·유지·착륙 | 미수신·중계 불일치·비행/Disarm 실패 |
| 모터 run | 같은 기준 배터리, 모터 1 약화, pause 동안 기간 정지, 자동 만료·명시 clear, 착륙 | 적용/해제·다른 채널 보존·joint/기체 반응을 확인하지 못함 |
| 배터리 run | 후기 프로파일, 동일 SOC 0.95, 고장 없이 같은 기본 비행 | 새 run 원점/프로파일·PX4 재출력 불일치 |
| 기록·전처리 | 매 run의 실제 raw 개수 대조, 같은 입력의 live/offline 행 대조 | 개수 차이·정답 혼입·준비 창 없음 |
| 종료 | 매 run 저장 cleanup, 소유 그룹·native IPC 종료 확인 | 강제 종료·잔류·저장 실패 |
| 선택 BIN | 명시한 기업 파일 하나 전체 read-only 재생·전처리·원문 SHA 재구성 | 파일 변경·바이트 유실·파서 실패 |
| 최종 원본 상태 | 성공/실패와 무관하게 원본 Git 상태 재확인 | 원본 변경 |

첫 실패 뒤 아직 실행하지 않은 단계는 **미실행**이다. 이전 단계가 통과했다고 전체 통과로 쓰지 않는다. 세 run은 같은 시험을 몰래 재시도하는 것이 아니라 서로 다른 정상/고장/프로파일 항목이다.

현재 실행기는 **headless**다. Gazebo GUI/QGC 창을 띄우지 않고 실제 PX4 SITL·Gazebo 프로세스를 운영한다. 창 없음과 가짜/합성 비행은 다른 개념이다. 합성 입력은 단위시험에만 사용한다.

## 2. 실행 명령

프로젝트 루트에서, 전체 작성 완료와 실행 승인을 확인한 뒤 사용한다.

```sh
PYTHONPATH= .venv/bin/python -B tests/integration.py \
  --out hermes/verification/first --jobs 4
```

기업 원자료를 한 파일 포함하는 경우:

```sh
PYTHONPATH= .venv/bin/python -B tests/integration.py \
  --out hermes/verification/first --jobs 4 --bin /path/to/flight.BIN
```

두 명령을 연속 실행하는 것이 아니다. **둘 중 하나만 선택**한다. `--bin`은 로컬 읽기 전용 입력이며 원본 복사/외부 업로드를 하지 않는다. 이미 `first` 결과 폴더가 존재하면 실행기는 거부한다. 실패를 숨기려고 폴더를 지우지 않는다.

배터리 단위시험의 기본 temporary directory는 결과 폴더 아래로 지정하고, 수집/자원 단위시험은 각각 `hermes/test-data`, `hermes/test-runtime` 안의 소유 임시 폴더를 사용한다. 빌드 자체는 시간이 걸릴 수 있어 단계별 상한을 두되, Git/연결과 각 상태 대기는 120초 이내다. `tools/build.py`의 빌드 명령별 제한은 1200초이며 통합 빌드 전체 상한은 2700초다. 기능 검사 중단 시 필요한 자원 종료는 수행한다.

### 승인된 콘솔 수정 후 추가 실행

최초 `first` 실행의 콘솔 응답 판별 실패를 보고한 뒤, 사용자가 수정 및 추가 통합 검증 1회를 승인했다. V2 `Child.command()`의 응답 경계와 합성 회귀 검사만 수정하고, 원본 PX4·센서 검사·파라미터 readback은 유지한다. 아래는 해당 추가 실행 명령이며, 이 역시 실패 후 자동으로 반복하지 않는다.

```sh
PYTHONPATH= .venv/bin/python -B tests/integration.py \
  --out hermes/verification/retry-console --jobs 4 --bin /path/to/flight.BIN
```

새 콘솔 회귀 검사는 결정론적으로 나눈 수신 문자열을 사용한다. 실제 PX4 PTY 응답 확인은 뒤의 정상 run에서 수행하므로, 합성 검사만으로 실제 콘솔 수정 성공을 선언하지 않는다.

### 승인된 resume 수정 후 추가 실행

두 번째 실행의 pause 해제 직후 heartbeat 신선도 실패를 보고한 뒤, 사용자가 복귀 처리 수정과 추가 통합 검증 1회를 승인했다. 수신 시각 경계 조건과 `resuming` 대기를 추가하고 기존 3초 신선도·비행 전 검사·원본 PX4/Gazebo는 유지한다.

```sh
PYTHONPATH= .venv/bin/python -B tests/integration.py \
  --out hermes/verification/retry-resume --jobs 4 --bin /path/to/flight.BIN
```

- 합성 회귀에서는 오래된 heartbeat, 경계 이전의 아직 신선한 값, 다른 송신자, 동일 fields의 새 수신, heartbeat만 있고 SIM 진행 없음, 미수신 제한 초과, 기존 프로세스/기록/경로 오류, 정상 감시 복귀, 종료 시 unpause를 구분한다.
- 실제 pause를 wall 3.2초로 두어 기본 heartbeat 신선도 3초보다 긴 정지 후의 복귀를 포함한다. 배터리 소비·고장 기간·SIM 시각은 정지해야 한다.
- 실제 raw에서 `resume_wait` 경계와 `resume_ready` 관측 사이에 새 PX4 heartbeat가 있는지 대조한다. `resume_ready` 자체를 수신 증거로 대신하지 않는다.
- 합성/실제 단계는 모두 이 한 번의 실행기 안에서 수행하며, 어느 단계든 실패하면 저장 후 중단한다. 앞 두 실행 원문을 덮지 않는다.

## 3. 숫자의 정확한 의미

- normal/fault에서 명령 수치 대조는 실제 동적 표본으로 한다. 정지 명령 0에 배율을 곱한 것을 약화 증거로 세지 않는다.
- `joint_rad_s`는 시뮬레이터 물리 관측이고 부호·slowdown을 확인한다. publish 성공만으로 물리 반응을 선언하지 않는다.
- 모터 run의 자세 변화는 해당 가상 실험의 반응이다. 탐지기 성능이나 실제 고장 원인을 증명하지 않는다.
- `input_age_sim_s_*`는 수신측 SIM 신선도다. 원명령에 생산 시각이 없으므로 end-to-end latency/무지연으로 부르지 않는다.
- 배터리 모델의 값과 PX4 재출력은 독립적으로 읽는다. component180 송신 성공만으로 component1 수신 성공을 선언하지 않는다.
- wire의 ID/온도 caveat를 숨기려고 원문·upstream을 고치지 않는다. 실제 관측 ID는 결과에 기록한다.
- live와 offline은 동일 저장 원문을 사용한 인과 전처리 행 비교다. 별개의 비행이 수치적으로 같다는 검사가 아니다.

## 4. 한 번의 기본 통합 검증으로 닫지 않는 항목

다음은 모듈 문서에 남긴 후속 강건성/비교 항목이며 **이번 기본 실행의 전체 통과 주장을 해서는 안 된다.** 이 목록은 실패한 항목을 사후 제외한 것이 아니라 실행 전에 정한 경계다.

- 중계 없는 stock 직접 연결과의 정량 지연·폐루프 비행 동등성. 정상 패스스루/비행 확인과 구분한다.
- 모터 2~4 각각의 실제 비행 고장. 1~4 문법/모델 배선 검사는 있지만 기본 비행 고장은 모터 1이다.
- native 모든 invalid/stale/reset/단절/output-failure 분기, 지연 callback과 막힌 pipe의 sanitizer·스트레스 검사.
- GUI/QGC, 다중 기체 동시 실행, 장시간 기록·디스크 한계, 라이브 world reset.
- 지정하지 않은 나머지 기업 BIN, 원자료의 정상 라벨/센서 교정/물리 타당성.
- CMU 원자료의 과학적 재추출·실기체 팩 보정·정밀 전기/추력 결합.
- AI 정확도·두 모델 학습/비교·완성 UI·실기체 연결/배포.

처음 승인된 정상 중계 지연 항목은 수신측 신선도 관측까지만 포함하며, **직접 연결 대비 무지연·완전 동등성은 미검증으로 보고**한다. 이 차이를 숨기고 모든 설계 항목을 닫지 않는다.
