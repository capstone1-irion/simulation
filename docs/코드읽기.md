# 코드 역할과 읽는 순서

목표는 **정상 데이터 흐름을 먼저 읽고, 필요한 실패/종료 처리만 따라갈 수 있게 하는 것**이다. V1의 import wrapper가 아니라 V2에서 독립 작성했다. AI 학습·완성 UI는 별도 과제다. 각 코드 첫머리에 역할·입력·출력·호출자를 한국어로 적었다.

## 1. 먼저 세 흐름을 구분한다

| 흐름 | 순서 | 마지막 산출물 |
|---|---|---|
| 비행·고장 | `main → Runtime → PX4 → motor_fault → stock 모터 → Gazebo 센서 → PX4` | 실제 시뮬레이션 운동·PX4 관측 |
| 배터리 | `motor_fault 원명령/시계 → gz_feed → BatteryLink → Battery → PX4 BATTERY_STATUS 입력` | PX4가 다시 송신한 배터리 관측 |
| 데이터 | `PX4 UDP → Collector → Preprocessor` 또는 `JSONL/BIN → iter_records → 같은 Preprocessor` | 인과적으로 정렬된 관측 행·창 |

배터리는 **고장 적용 뒤 joint 속도가 아닌 원래 요구 명령**으로 부하를 계산한다. `motor_fault`의 출력·고장 번호·joint 관측은 정답 폴더로 가며 전처리 특징으로 합치지 않는다. 수집기는 제어 명령을 송신하지 않는다.

## 2. 추천 읽는 순서

| 순서 | 파일 / 처음 볼 함수 | 역할·입력→출력 |
|---|---|---|
| 1 | `main.py: arguments, simulate` | 사용자의 CLI를 책임별 기능으로 전달한다. `simulate`와 자동 비행 `experiment`를 구분한다. |
| 2 | `capstone/scenario.py: run_scenario, takeoff, land` | 실험 순서와 정상 preflight/이륙/착륙 확인. GCS heartbeat는 이곳의 독립 송신자다. |
| 3 | `capstone/simulation.py: start` | 고정 소스 확인, 새 run, 센서 서버, PX4, 배터리·수집 연결을 소유한다. |
| 4 | `capstone/battery.py: Battery.update, _current` | JSON 프로파일+원명령+SIM 초 → V/A/SOC/mAh. 네트워크가 없는 계산 부분이다. |
| 5 | `models/capstone_x500/model.sdf` | x500_base를 그대로 포함하고 모터 입력만 applied topic으로 연결한다. |
| 6 | `native/motor_fault.cpp: PreUpdate` | 정상 원문 복사, 한 모터 배율, 기간 만료/clear. 물리 힘 계산은 stock 모터가 한다. |
| 7 | `capstone/battery_link.py: _read, _send` | 상태 수신→배터리 계산→표준 wire 단위 송신. 정답을 별도로 기록한다. |
| 8 | `native/gz_feed.cpp: main` | Gazebo StringMsg를 가공 없이 Python stdout으로 전달한다. |
| 9 | `capstone/collector.py: _run, _decode, _write` | 독점 UDP 수신, 원문 먼저 저장, 해석 결과와 콜백 전달. |
| 10 | `capstone/replay.py: iter_records, _bin` | 원래 기록 순서와 실제 시계를 유지해 V2 외피로 읽는다. |
| 11 | `capstone/preprocess.py: consume, _advance` | 소스별 단위/의미, 10 Hz 인과 정렬, null/mask/age, 50행 창. |
| 12 | `capstone/simulation.py: healthy, close` 및 `capstone/processes.py` | 벽시계 제한, 프로세스·파일·IPC 소유권, 실패와 종료를 읽는다. |

`simulation.py`가 가장 길지만 배터리 수식·원문 해석·전처리를 그 안에 넣지 않았다. `main.py`는 얇은 진입점이고 `Runtime`은 한 run만 소유한다. 실행 중 reset/프로파일 교체·범용 plugin manager·원격 API 서비스는 만들지 않았다.

## 3. 핵심 코드별 작은 안내

### `motor_fault.cpp`

- `Mailbox`: transport 스레드와 시뮬레이션 스레드가 나누는 상태. callback이 해제된 plugin을 가리키지 않게 한다.
- `Parse/Request`: 문법을 확인하고 요청을 대기 슬롯에 넣는다. **수락은 적용 성공이 아니다.**
- `Configure`: 실제 모델 이름으로 토픽·서비스·joint 관측을 연결한다.
- `PreUpdate`: SIM 시간이 진행하는 tick에서만 정상 중계/고장을 적용한다.
- `PostUpdate`: 물리 이후 joint를 관측하고 상태를 발행한다. force를 쓰지 않는다.
- `Reset`: 원점이 바뀐 시간을 기존 run에 이어 붙이지 않고 실패로 보고한다.

외부 모터 번호는 1~4, protobuf/SDF 인덱스는 0~3이다. 위치·방향 표는 `docs/모터중계.md`에 있다. 원명령과 적용 명령은 rad/s 목표값이다. `joint_rad_s`는 slowdown을 복원한 시뮬레이션 정답이며 실제 센서 RPM처럼 취급하지 않는다.

### `battery.py`

1. `load_profile`: 정확한 ID/JSON 경로를 읽는다. 비슷한 ID로 자동 대체하지 않는다.
2. `_current`: 네 원명령을 부하표의 전류로 바꾸어 합산한다.
3. `update`: 직전 전류와 SIM 시간 차이로 소비량을 적분하고 SOC를 갱신한다.
4. SOC별 등가 OCV에서 내부저항 강하를 빼 단자전압을 계산한다.
5. 유효성을 확인한 뒤에만 새 상태를 반영한다.

상대 SOH/용량/저항/출처는 **프로파일**, 시작 SOC/소비량 원점은 **초기 상태**, V/A/SOC/mAh는 **실시간 모델 상태**다. 세 개념을 혼동하지 않는다. 같은 SIM 시각은 적분하지 않고, 시간 역행·긴 공백·결측은 정상 0이 아니라 오류다.

### `collector → replay → preprocess`

`Collector._write`가 저장을 먼저 완료하고 `on_record`를 호출한다. raw에는 필터 밖 메시지도 보존하고, `latest()`와 전처리에서 선택 기체/component를 적용한다. BIN은 MAVLink로 위장하지 않으며 원래 `TimeUS`가 없으면 시간을 만들어 넣지 않는다.

`Preprocessor.consume`는 입력 시각보다 앞선 tick을 먼저 확정한다. 따라서 나중 값을 과거 빈칸에 채우지 않는다. 오래된 값은 `null`과 `mask=false`로 바뀐다. 배터리 입력이 준비되었다고 모터/기체 응답 입력까지 준비된 것은 아니므로 두 준비 조건을 따로 계산한다.

실시간 CLI는 최근 창을 메모리에 유지하고 원문을 저장한다. 영구 특징 파일이 필요하면 종료한 원문에 `main.py preprocess`를 실행한다. 실시간 행을 별도 저장하는 소비자는 `Preprocessor(on_event=...)`를 연결한다. 겹치는 창 전체를 매번 디스크에 복제하지 않는다.

### `processes.py: Child.command`

PX4 콘솔은 글자를 받을 때마다 `pxh> `를 다시 표시한다. 따라서 첫 프롬프트를 발견했다고 명령이 끝난 것은 아니다. `command()`는 **보낸 명령 전체의 echo와 Enter 개행 → 응답 → 새 줄의 완료 프롬프트**를 기다리고, 가운데 응답만 반환한다. ANSI 장식·분할 수신은 누적 버퍼에서 처리한다. 출력이 없는 정상 명령은 빈 문자열을 반환한다.

명령 전송 전 timeout 범위를 확인하며, 완료 프롬프트 미수신·콘솔 종료·기록 오류는 실패로 남긴다. 응답을 받았다는 사실만으로 명령 성공을 선언하지 않는다. `Runtime.parameter()`의 숫자 readback과 비행 상태 확인은 그대로 유지한다. 콘솔 입력/전체 원문은 `px4.log`, 분리된 명령 응답은 `groundtruth/events.jsonl`에 남는다.

### `simulation.py: pause` — 재개와 새 수신 확인

일시정지 동안 SIM 시간과 배터리 적분은 멈추지만 PC 단조 시계는 진행한다. 따라서 이전 heartbeat의 수신 시각을 그대로 두면 재개 직후에도 오래된 값일 수 있다. 단순히 `paused=false`만 확인하고 비행으로 넘어가지 않는다.

1. 재개 요청 동안 상태를 `resuming`으로 둔다. Gazebo 서비스 응답과 실제 `paused=false` readback을 각각 제한 시간 안에 확인한다.
2. readback 뒤 PC 단조 ns를 경계로 기록한다. 그 **경계보다 뒤에 실제로 수신한 PX4 component1 heartbeat**와 기존 SIM 시각보다 진행한 새 상태를 최대 5초 기다린다.
3. 대기 중에도 프로세스/로그/수집/배터리/모터 경로·모터 상태 수신·SOC·GCS·디스크 오류를 감시한다. pause로 오래된 SIM 시계와 heartbeat는 이 제한된 복귀 조건으로 검사한다.
4. 조건 충족 뒤 `running`으로 돌아가 기존 heartbeat 3초·시계 5초 신선도 검사를 즉시 다시 수행한다. 실패하면 `failed`로 남고 호출자가 종료한다.

`Collector.latest(..., since_monotonic_ns=...)`는 원래 수신 시각을 비교할 뿐 수정하지 않는다. fields가 같아도 새 패킷이면 인정하지만, 경계 이전 값·다른 system/component·이미 stale한 값은 인정하지 않는다. 수집은 여전히 수신 전용이다. `resume_wait`/`resume_ready`는 정답 이벤트에만 남기며 원문 heartbeat 수신 시각과 대조할 수 있다.

종료 중의 unpause는 별도다. 기존 오류 때문에 정리가 막히지 않도록 `stopping` 상태에서는 새 heartbeat 복귀를 요구하지 않고 세계 해제 readback 후 원래의 착륙·자원 종료 경로를 진행한다. 이것을 정상 복귀 성공으로 기록하지 않는다.

| `profiles/battery/provenance.json` | 이전 데이터의 근거·라이선스·과거 주장·이전 hash 구분 |

| `tests/test_runtime.py` | 콘솔 응답·resume 새 수신/시계/제한/오류/종료 경계, 소유 자원·배터리 wire·승인된 SDF 변경만 존재하는지 |

`external/`은 원본 의존성, `.venv/`는 설치 환경, `hermes/`는 생성 산출물이다. 이 세 폴더를 우리 제품 소스 목록에 섞지 않는다. 기존 V1 폴더를 삭제해도 **설치된 V2의 제품 실행은** V1 코드/환경을 찾지 않는다. 단, 명시적으로 V1의 기업 BIN을 입력 경로로 지정한 분석은 그 원자료를 읽는다.

## 5. 다음 팀원의 책임

- 기업 로그는 기록 당시 펌웨어·배터리/IMU 인스턴스·단위·시계 기준을 선언한다.
- `battery_ready` / `motion_ready`가 false이면 정상 판정으로 대체하지 않는다.
- 데이터셋은 run/비행 단위로 먼저 분리한다. 정규화 통계는 정상 TRAIN에서만 학습한다.
- PX4와 ArduPilot의 명령/진동 의미 차이를 지우고 하나의 scaler/가중치를 공유하지 않는다.
- 정답 폴더·프로파일 ID·고장 배율·파일 경로를 모델 특징으로 쓰지 않는다.
- 모터 위치 식별·이상탐지 정확도·학습 모델 2종 비교는 이번 코드 작성 완료와 별도로 검증한다.
